When to use it

Build, debug or review Elementor and Elementor Pro sites. Use for safe page and template edits in _elementor_data, custom widgets, dynamic tags, Pro form actions and Theme Builder locations, blank or stale renders and CSS caches, free vs Pro checks and proving an extension works on a staging site.

Boundaries and hand-offs

ACF or Secure Custom Fields field design and values behind Pro ACF dynamic tags to wp-devkit-acf-and-content-modeling; WooCommerce Builder widgets with store behavior to wp-devkit-woocommerce-dev; theme templates, child themes and Hello-based themes to wp-devkit-theme-development; plugin lifecycle and packaging of an add-on to wp-devkit-plugin-development; XSS or authorization defects with a reachable path to wp-devkit-security-review; measured whole-site slowness to wp-devkit-performance-review; bulk content operations to wp-devkit-wpcli-and-ops; layout and visual design to wp-devkit-ui-design.

What it covers

The agent loads only the reference that matches the task:

  • custom-widgets.md: read for classic and atomic widget scaffolds, controls, rendering and assets.
  • deploy-and-verify.md: read to install and prove an extension on staging.
  • dynamic-tags-forms-and-theme-builder.md: read for dynamic tags, Pro form actions and Theme Builder locations.
  • free-vs-pro-matrix.md: read to answer free versus Pro questions.
  • page-data-and-content-edits.md: read for _elementor_data, safe content edits, templates, global widgets, kits and page building.
  • render-debugging-and-caches.md: read for blank or stale output, cache layers and damaged data.
  • third-party-notices.md: license notice for material adapted from Mekko Digital elementor-skills.

How a review runs

  1. Name the surface: page content, templates and kit, custom extension code, or render and cache behavior. Check versions and experiments first; the classic and atomic editors use different data shapes and code paths.
  2. For extensions, trace registration hook, class base, control definitions, render() and content_template() output, assets and dependencies. Check escaping at each sink and that render() reads get_settings_for_display().
  3. For content, read _elementor_data as JSON for the affected post only. Identify shared sources (global widgets, kit, Theme Builder templates, translations) before attributing a change to one page.
  4. For render problems, place the failure (editor, preview, frontend) before touching caches. Cache regeneration that hides a defect is not a fix.
  5. For Pro features, confirm Pro is active and that the feature is registered on this install; do not rely on the static matrix alone.
  6. Classify by reachable impact. Escaping gaps in a widget only an administrator can configure still need the actor and path named. A finding needs a reachable path and impact. A style preference is INFO. Missing evidence (no staging copy, unknown Pro version, unknown experiments) is a valid outcome: say what is missing and how to get it.

What you get back

Review: result and scope first. Each confirmed finding: severity per the contract, file:line or post ID and element ID, actor, trigger, reachable path, impact, confidence, minimal remediation, regression check. Candidates and missing evidence in a separate list.

Implementation: changed boundaries, backups taken, commands run with exit status, registration and render results, caches regenerated, checks not run, residual risk, rollback.

Reviews are read-only. A clean review covers the inspected scope; it is not a certification. Ask for implementation as a separate, bounded task with a regression check.
